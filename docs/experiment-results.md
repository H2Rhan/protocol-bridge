## 摘要（一句话结论）

**记忆注入不是免费的：同一份记忆，注入方式不同可以让 API 成本相差约 7.3 倍。**
只有当「内容锁死 + 确定性序列化 + 置于前缀头部 + 超过该模型最小可缓存阈值」四者同时满足时，KV 前缀缓存才生效；一旦失效**不报任何错**，只体现为账单变贵。

核心主数字（20 轮长对话，同一模型）：

| 注入方式 | 稳态命中率 | 20 轮相对成本 |
| --- | --- | --- |
| LOCKED（会话内锁死） | 94.9% | 1× |
| DYNAMIC（每轮重写） | 0.0% | **7.35×** |

> 该倍数在 haiku-4.5 实测为 7.35×、在 sonnet-4.6 实测为 7.30×，**与模型无关**，可作为跨模型引用的稳定主数字。

## 二、三大必做维度（exp1–exp3）

### 1. 更新频率

| 组 | 做法 | 稳态命中率 | 相对成本（8 轮） |
| --- | --- | --- | --- |
| B_locked | 会话开始注入一次并锁死 | **98.1%** | 1× |
| C_dynamic | 每轮动态注入（前缀每轮变） | **0.0%** | **10.2×** |

精确公式（exp9，独立盐隔离验证）：每 N 轮更新一次的稳态命中率 = **(N−1)/N**。
实测 N=1→0%、N=2→49.9%、N=3→66.5%、N=5→66.5%，与理论 0/50/66.7/80 吻合。

### 2. 位置

| 组 | 做法 | 稳态命中率 | 相对成本 |
| --- | --- | --- | --- |
| D1_head | 记忆放前缀头部（system） | **98.1%** | 1× |
| D2_tail | 记忆放消息流尾部（append） | **14.1%** | **7.9×** |

D2_tail 出现**「第 3 轮崩塌」**：前 2 轮命中，第 3 轮起因历史累积使前缀每轮变化，写入量随轮次递增（2952→3007）。这是「缓存如何失效」的最佳实证。

### 3. 粒度

| 组 | 做法 | 稳态命中率 | 说明 |
| --- | --- | --- | --- |
| G1_300 | 单块约 300 token | **0.0%** | 低于阈值，**静默不缓存**（无报错） |
| G2_4×512 | 4 条 × 512 token 多断点 | **97.8%** | 断点是**前缀累积**，不是按块独立判断 |
| G3_2048 | 单块 2048 token | **97.8%** | 超阈值稳定命中 |
| G4_30frag | 30 条细粒度 | **98.8%** | **未触发 20-block 断崖** |

## 三、硬约束验证

### 最小可缓存长度（逐模型，不可外推）

| 记忆实际 token | haiku-4.5 | sonnet-4.6 | opus-5 |
| --- | --- | --- | --- |
| ~1237 | ✗ | ✗ | ✗ |
| ~2453 | ✗ | ✗ | ✗ |
| ~3581 | ✗ | ○（1436 起即缓存） | ✗ |
| ~4162 | ○ | ○ | ✗ |
| ~5936 | ○ | ○ | **✗（端点异常，见 E34）** |

- **sonnet-4.6**：阈值 ≤ 1436（符合文档 1024 档）。
- **haiku-4.5**：E23 精确扫描得实际阈值夹在 **3581（不缓存）~ 4162（命中）** 之间，即 **4096 token**（与官方文档精确吻合）。
- **opus-5**：大 token 请求返回 `input_tokens=0`（请求未正常处理），**非「不缓存」而是「端点不可用」**，缓存行为无法可靠验证（E34 复测 8000–20000 token 四档均返回空 usage）。结业文档应表述为「端点异常、待复测」，不可写成"不缓存"。

### 断点上限（硬约束）

| 断点数 | 结果 |
| --- | --- |
| 1 | 0.0%（800 token 未过阈值，静默不缓存） |
| 2 | 66.3% |
| 4 | 83.2% |
| **5** | **HTTP 400「A maximum of 4 blocks with cache_control」** |

→ **4 个断点是硬上限**，第 5 个直接报错（非静默降级）。4 个名额应放在最稳定的分界：tools 后 / system 后 / 历史静态段后 / 滚动尾部。

### 20-block 回看窗口（已证伪删除）

5 块（920 token）0%、10 块 99.8%、30 块 99.9%、**60 块 100%（10872 token 全读）**。
→ 「20-block 回看窗口」在 sonnet-4.6 上**不成立**；真正的硬约束是**最小可缓存长度**，不是 block 数。该条已从执行方案删除。

### 顺序稳定性（确定性序列化硬要求）

| 组 | 做法 | 命中率 |
| --- | --- | --- |
| O1_fixed | 固定顺序 4 条记忆 | **74.8%** |
| O2_shuffled | 同样 4 条只换顺序 | **24.9%** |

→ 记忆检索按相关度打分排序会导致抖动，注入前**必须稳定排序**。

### TTL（缓存空闲有效期）

| 配置 | 建立 → 立即重发 | 空闲 400s 后 |
| --- | --- | --- |
| T1_5min（默认） | 命中 ✅ | **已失效，重新写入**（5min 档过期） |
| T2_1h（显式 ttl） | 命中 ✅ | **仍命中**（1h 档真实生效） |

→ Responses → Anthropic 方向的 TTL 只能从 24h 降级为 1h，且 1h 档在端点侧是**真实生效**的（非名义支持）。

## 四、协议形态与 05B 方向

### 三协议横向对比（exp6）

| 协议端点 | 稳态命中率 |
| --- | --- |
| Anthropic Messages（/v1/messages） | 99.7% |
| OpenAI Chat（/v1/chat/completions） | 99.7% |
| OpenAI Responses（/v1/responses） | **0.0%**（三轮 cache 字段全 0） |

### token 口径不对称（exp4，四轮逐字吻合铁证）

同一段对话，E1 真实总输入（input+cache_read+cache_creation）= 2981/2992/3004/3016，与 E2 `prompt_tokens` 完全相同：

- Anthropic `input_tokens` **不含**缓存（第 2 轮仅 20）——直接当输入量会**少算 99.3%**；
- OpenAI `prompt_tokens` **包含**缓存；
- OpenAI 格式第 1 轮即 99.7% 命中 → **协议转换不损失缓存能力**，但 usage 口径必须归一。

### 05B 救援实验（E27，决定性）

| 后端 | 命中率 | 结论 |
| --- | --- | --- |
| (a) 透传 /v1/responses | 0.0% | 该 Responses 端点不实现缓存透传 |
| (b) 转换器产出 → /v1/messages | **99.85%** | **05B 缓存可达** |

→ **05B 方向缓存收益可达，前提是转换器后端走 Anthropic Messages 原生端点，而不是把 Responses 透传到 Responses 端点。** 即转换层必须做 Responses→Messages 转换（正是 TRACK 05 的本职），不能做 Responses→Responses 透传。此结论将原「05B 告急」改写为「05B 可行，但落点必须正确」。

## 六、回写执行方案的修正建议

1. **05B 方向结论改写**（最高优先级）：从「缓存收益可能不可达」改为「**可达，前提后端走 Messages 端点（Responses→Messages 转换），禁止 Responses→Responses 透传**」。
2. **删除「20-block 回看窗口」**：已决定性证伪（60 块 100% 命中）。
3. **最小缓存阈值查表**：sonnet-4.6 ≈ 1024、haiku-4.5 ≈ 4096、opus-5 端点异常无法验证（E34）。「记忆做多大才划算」必须逐模型实测，不可外推。
4. **工具 schema 稳定序列化**：工具定义纳入前缀稳定性约束，变更即缓存失效（E22）。
5. **多模型网关的缓存不共享**：统一前缀策略需按 provider/模型分别建缓存（E20）。
6. **流式可放心开启**：不影响缓存命中率（E21）。
7. **主数字跨模型一致**：LOCKED vs DYNAMIC ≈ 7.3×，可直接引用（E28）。
8. **冷启动 single-flight 必要**：并发冷启动会系统性重复写入（E32，N=6 平均 3 次/轮），网关冷启动需单飞或串行预热兜底。
9. **修正 opus-5 结论**：不是"不缓存"，是端点异常（返回 input=0），不可写成硬结论（E34）。
10. **缓存无长度上限 + 命中省 ~1.65s**：记忆做到 23711 token 仍全缓存（E34）；命中比冷启动快 ~1.65s（E33）。

## 七、方法学与踩坑（务必沿用）

1. **前缀隔离**：每个实验配置必须加独立随机盐。曾因配置间共享记忆内容，后跑配置复用先跑配置的缓存，跑出「每 2 轮更新仍 99.7%」的假象。加盐后数据回归理论值。
2. **token 数不能靠估算**：字符/token 系数须按实测校准（sonnet-4.6 约 5.1 字符/token，脚本取 6 留余量）。估算偏小会导致「自称 1200 token 实际 940」低于阈值，产出假阴性。
3. **真实 API 网络不稳定**：脚本必须带指数退避重试，否则整组配置数据丢失。
4. **流式解析**：`stream` 既要在请求体里声明，也要在解析端按 SSE 处理，否则按 JSON 解析 SSE 文本报错。
5. **预热**：`max_tokens:1` 预热成功写入后，正式请求 100% 命中——预热从「建议」升级为「实测有效」。
6. **并发冷启动要跑多轮**：单轮结果会因网络到达时序波动（E30 单轮 N=3 有 2 次重复、N=6 只有 1 次），多轮统计（E32）才揭示「重复写入是常态」。并发请求用 `threading.Barrier` 同时出发，但网络到达仍有毫秒级差异，落在「缓存建立窗口」内的数量是随机的。
7. **延迟测量用中位数**：海外端点延迟波动大，均值易被离群慢请求拉偏（E33 命中均值 3.73s、中位数 3.10s）。对比「命中 vs 冷启动」要同网络、多次采样、取中位数。
8. **区分「不缓存」与「请求异常」**：opus-5 大 token 请求返回 usage 空（`input_tokens=0`），是请求未正常处理，不是「不缓存」。下结论前先核对 `input_tokens` 是否正常，否则会把「端点挂了」误判成「模型不缓存」（E34 的教训）。
